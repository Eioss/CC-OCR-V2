================
The Modular Asset State System (MASS) is a state-management system designed for [Unity](http://unity3d.com).

MASS provides a structured framework for managing the state of in-game assets, components and other game objects, with a particular focus on driving animation transitions and state changes in a modular, decoupled way.

This is a foundation library, not a turnkey solution; it gives you the architecture to build state-driven behavior on top of, while leaving the specifics of your game logic up to you.

> ⚠️ **Status:** Early development. APIs are subject to change.

Overview
--------
At its heart, MASS is built around the idea that the *state* of an asset and the *representation* of that state (animations, visuals, behaviors) should be independent of one another. Game logic decides what state something is in; MASS handles propagating that decision to all the subsystems that care.

This separation lets you:

- Swap out animation systems without touching game logic.
- Drive multiple representations from a single source of truth.
- Test state logic in isolation from the rendering layer.
- Compose complex behavior from small, reusable state modules.

---
Core Concepts
-------------
**State** — A named, serializable description of where an asset currently is. States are intentionally lightweight; they carry no behavior of their own.

**State Machine** — Owns a set of states and the valid transitions between them. Enforces transition rules and emits events when transitions occur.

**Module** — A self-contained unit that reacts to state changes. Animation drivers, audio drivers, and visual-effect controllers are all modules. Modules subscribe to a state machine and translate its output into observable behavior.

**Asset** — The game object being managed. An asset binds together a state machine and one or more modules.

Installation
------------
MASS is distributed as a Unity package. The recommended way to install is via the Unity Package Manager using a Git URL.

1. Open your Unity project.
2. Open **Window → Package Manager**.
3. Click the **+** button and choose **Add package from git URL…**
4. Enter the repository URL and confirm.

Manual installation by copying the source into your `Assets` folder is also supported, but the Package Manager approach is preferred for easier updates.

Quick Start
-----------
A minimal MASS setup involves defining your states, wiring up a state machine, and attaching a module to react to changes.

```csharp
// Define your states
public enum DoorState { Closed, Opening, Open, Closing }

// Create a state machine on your asset
var machine = new StateMachine<DoorState>(DoorState.Closed);

// Define valid transitions
machine.AddTransition(DoorState.Closed, DoorState.Opening);
machine.AddTransition(DoorState.Opening, DoorState.Open);
machine.AddTransition(DoorState.Open, DoorState.Closing);
machine.AddTransition(DoorState.Closing, DoorState.Closed);

// React to state changes
machine.OnStateChanged += (from, to) =>
{
    Debug.Log($"Door transitioned from {from} to {to}");
};

// Drive the machine from your game logic
machine.TransitionTo(DoorState.Opening);
```

From here you would attach an animation module that listens to `OnStateChanged` and plays the appropriate clips.

Architecture
------------
MASS follows a layered design:

```
┌─────────────────────────────────────┐
│           Game Logic Layer           │  ← decides state changes
├─────────────────────────────────────┤
│          State Machine Layer         │  ← validates & emits transitions
├─────────────────────────────────────┤
│             Module Layer             │  ← reacts to transitions
├─────────────────────────────────────┤
│   Representation (Animation/Audio)   │  ← observable output
└─────────────────────────────────────┘
```

Each layer only knows about the layer directly below it. Game logic never touches animation directly; it only ever talks to the state machine. This keeps the dependency graph clean and makes each layer independently testable.
